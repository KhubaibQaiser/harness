# Judge fit for judgement rules in the adherence report

Date: 2026-11-05. Question: is a model judge a good fit for judgement rules ("ask before deciding", "plain communication", "no invented data", "fix everything found", "smallest change")? Which candidate?

Labels: **UNVERIFIED** = could not confirm from a primary source. **Estimate** = my arithmetic, not a measurement. **Vendor claim** = published by the party selling it.

---

## 0. Verdicts

| Candidate | Verdict | One-line reason |
|---|---|---|
| 1. Laya | **Poor fit** | 512-token English context, near-chance zero-shot, known negation failure, needs fine-tuning on labelled data we do not have. |
| 2. Local open LLM judge (Ollama) | **Partial fit** | Fine as an opt-in judge for short windows with a narrow yes/no question. Not reliable on whole transcripts. Accuracy for our rules is UNVERIFIED and must be measured. |
| 3. Hosted Claude judge | **Partial fit (best accuracy, still not proven)** | Cheap at window scale, but no published accuracy for this task, and the literature shows even strong judges miss. Paid and opt-in only. |
| 4. Heuristics only | **Fit for what it can count** | Exact and free, but it only detects the *absence of a signal*, not whether a judgement was good. Should be the base layer. |

**Recommendation:** heuristics find and score candidate windows (always on). An optional judge reads only those short windows and answers one yes/no question each, with a "can't tell" outcome. Report judge results as "flagged for review" with the window quoted, never as a pass/fail grade. Default judge: local Ollama model. Hosted Claude as an opt-in upgrade. Do not ship Laya. Details in section 5.

## 1. Laya

### Facts (from the repo README and Hugging Face card)

- **Context length.** Three checkpoints ([README](https://github.com/NandhaKishorM/laya), [HF card](https://huggingface.co/convaiinnovations/laya)):
  - `laya`: ModernBERT-large, 421M, **512 tokens**, English. The card says the head budget is 192 tokens, leaving about 320 for the text.
  - `laya-multilingual`: mmBERT-base, 322M, 1,024 by default, extendable to **8,192** with `max_len=8192`.
  - `laya-typed-decisions`: 421M, 1,024.
- **Long input.**
  - Default multilingual limit "cuts long documents off", so long text is silently truncated unless you raise `max_len`.
  - The card reports 16 to 18 of 20 correct up to about 4,000 tokens, and 8 to 17 of 20 beyond that. It advises testing on your own data. That is a 20-item check, not a benchmark.
  - A 4,000-token input takes about 1.7 s on an Apple GPU.
  - Long, mostly English text may route to the English checkpoint, so you must force `model="multilingual"`.
  - The MCP tool `laya_predict_long` scans in overlapping windows and reports which window supports the answer.
  - A separate "vegaml" mode (a frozen 0.8B reader) is said to read up to 73,728 tokens. The README gives no benchmark for it. UNVERIFIED.
- **Multi-turn / agent judging.** The README has no dialogue results. The closest items: a browser-agent case where element top-1 accuracy went from 0.10 to 0.66 after fine-tuning, and an "agent-trace observability" workflow that scores 0.730 on its own typed-decisions benchmark. Neither is rule-adherence judging of a coding agent. I found no result on long-document, dialogue or agent-trajectory *judging*.
- **"Honest limits" section (as read):**
  - It is "a fast base to specialise, not a zero-shot decision engine". Zero-shot scores are 0.362 and 0.352 on typed-decisions, **below the 0.461 majority-class baseline** (random is 0.318). The 0.766 headline needs fine-tuning on that benchmark's training split (about 4 to 5 hours for 4 epochs over about 30k questions on 2x T4).
  - **Negation:** on five cancellation examples, `laya` picked `cancel_account` for all four negated requests. One multilingual wrong answer carried 0.9998 probability.
  - Both checkpoints are over-confident as shipped. Calibrate on your own data.
  - Ordinal `score` is the weakest primitive (SST-5 0.372). `laya-multilingual` has a position bias on `score` (issue #131). Do not use yes/no or true/false labels in `choice` questions.
  - `noul` (yes/no probability) can follow its option labels rather than the text; criteria-less `noul` on `laya` gives the same answer whatever the input (issue #156).
- **"Where Jev leads" section.** It is a comparison with a competitor (Jev) on label-heavy tasks: Banking77 0.870 (Jev, 72 labels) vs 0.425 (Laya, 77 labels), soft accuracy 0.580 vs 0.471, raw calibration (ECE) 0.213 vs 0.144 before temperature scaling. Not relevant to a handful of yes/no questions, except that it confirms raw calibration is weak.
- **Weights licence.** Apache 2.0 (HF card metadata). Base ModernBERT-large is also Apache 2.0 per a third-party port, which is a secondary source.
- **Speed (README).** 32.8 to 39.5 ms per question on a T4 GPU. On a short email with four questions: 453 ms on CPU, 146 ms on Apple MPS for `laya`.
- **Install.** Python 3.10 or newer, PyTorch, about 2.3 GB of checkpoints for the three models. Harness is an npm package, so this adds a Python runtime and a large download.

### Why it is a poor fit here

1. Our evidence is agent behaviour across several turns, with tool calls. Even one decision window (user message, assistant reply, a tool call, a result) can exceed 512 tokens once code or diffs are in it.
2. Zero-shot it is below the majority baseline. Making it work means fine-tuning on labelled adherence data. We have none, and the owner's rule is no invented data.
3. Negation is a documented failure. Our rules are mostly negations or absences ("did not ask", "no trailer", "did not fix"). That is the exact weak spot.
4. It is built for classifying text into typed decisions, not for reading what an agent did.

Possible narrow use later: a fine-tuned classifier for a single, well-labelled question. Not now.

## 2. What the literature says about judging agent trajectories and multi-turn rule adherence

No source I found measures judge accuracy as a function of agent-trajectory length, or compares small and large judges on long agent transcripts. That gap is itself a finding: the design cannot lean on published accuracy for "whole 100k-token session" judging.

### 2.1 Judges on agent trajectories are mediocre, even large ones

- **AgentRewardBench** (web-agent trajectories, expert-labelled; [paper](https://arxiv.org/html/2504.08942v2)). Success detection, precision / recall:
  - GPT-4o with accessibility-tree input: 69.8 / 83.1. Claude 3.7 Sonnet: 68.8 / 81.6. Llama 3.3: 67.7 / 79.0. Qwen2.5-VL: 64.3 / 89.8. GPT-4o Mini: 61.5 / 86.1.
  - The paper says no judge exceeds 70% precision, so about 30% of "success" calls are wrong.
  - **Side-effect detection precision was 6.6% to 14.1% for every judge.** Repetition detection was much better (78.6% to 92.3% precision).
  - Rule-based scoring had the highest precision (83.8) but the lowest recall (55.9).
  - The paper does not give a general small-vs-large comparison; GPT-4o Mini was a little lower than GPT-4o on success precision.
  - Relevance: "did the agent do something it should not have" is the closest analogue to our rules, and judges were worst there. Countable things (repetition) were judged well.
- **Agent-as-a-Judge** ([arXiv 2410.10934](https://arxiv.org/abs/2410.10934), ICML 2025). On a 55-task code-generation benchmark (DevAI), alignment with human consensus was 83.88 to 92.07% for Agent-as-a-Judge vs 60.38 to 84.15% for plain LLM-as-a-judge. Single humans averaged 85 to 89%. Cost: $30.58 and 118 minutes vs $29.63 and 11 minutes for the LLM judge ([HF page](https://huggingface.co/papers/2410.10934), figures from the paper). Caveat: this judges "did the output meet a stated requirement" using tools to inspect the workspace. It is not a transcript-behaviour judge, and the requirements were predefined and checkable. A secondary summary notes the open-ended case is not covered.
- **tau-bench** ([Sierra blog](https://sierra.ai/blog/benchmarking-ai-agents)) is not a judge benchmark; it measures the agent. It shows that agents follow policy documents unreliably (GPT-4o pass^8 below 25% in retail, a ~60% drop from pass^1). This supports the product need, but says nothing about judge accuracy.
- **Counsel** dataset ([report](https://atlaai-counsel-tech-report.static.hf.space/index.html)) collects human meta-evaluations of open-weight judge critiques on tau-bench and DA-Code agent trajectories. I could not read its results section. UNVERIFIED what it found.

### 2.2 Long inputs and biases

- Models use long context unevenly: accuracy is highest when the relevant fact is at the start or end and drops in the middle ([Lost in the Middle](https://arxiv.org/abs/2307.03172)).
- LLM judges show position, verbosity and self-enhancement bias and limited reasoning; GPT-4 reached over 80% agreement with humans on chat preference tasks ([Zheng et al.](https://arxiv.org/abs/2306.05685)). That is preference between two answers, not rule adherence in agent logs.
- A 2026 study of nine debiasing strategies on five frontier or mid-tier judges found agreement on MT-Bench of 58% to 66% at baseline, negligible position bias, but verbosity bias for some models (Llama +0.44, Gemini 2.5 Pro +0.40, Claude Sonnet 4 -0.12) and the largest bias was style (markdown over prose, 0.10 to 0.76). It does not vary input length or model size ([arXiv 2604.23178](https://arxiv.org/html/2604.23178)).
- A June 2026 benchmark reports a "clear reliability gap" for LLM judges on long outputs (average 9,249.7 tokens). Judge performance did not fall monotonically with length. I only saw the abstract and third-party summaries ([alphaxiv](https://www.alphaxiv.org/abs/2606.01629)). The summary-level claim is UNVERIFIED against the full paper.

### 2.3 Small vs large judges

- **Small judges are weak at general judging.** In RocketEval, sub-3B models used directly reach only 21.7% to 39.2% instance-level agreement with MT-Bench human labels ([paper](https://arxiv.org/html/2503.05142)).
- **Judge-tuned small models.** Prometheus 2 (7B, Mistral-based), Flow-Judge-v0.1 (3.8B, Phi-3.5-mini) and Selene-1-Mini (8B, Llama 3.1) report strong results on their own benchmarks. Those are developer-run (vendor claims):
  - Flow-Judge: pass/fail F1 0.955 on its held-out set vs gpt-4o-mini 0.910 ([model card](https://huggingface.co/flowaicom/Flow-Judge-v0.1)). **Its context is 8,192 and the card says it was not trained on long-context inputs.** It is English only.
  - Selene-1-Mini: 128K context, Apache 2.0, claims to beat GPT-4o on RewardBench, EvalBiasBench and AutoJ ([model card](https://huggingface.co/AtlaAI/Selene-1-Mini-Llama-3.1-8B)). No scores on the page.
  - Prometheus 2: needs its own prompt templates for absolute or relative grading; English only ([model card](https://huggingface.co/prometheus-eval/prometheus-7b-v2.0)).
  - An independent comparison found GPT-4o and Claude 3.5 Sonnet "far exceed" small judges (Glider, Selene Mini, Flow Judge, Phi-mini) on general rubrics ([Galtea](https://galtea.ai/blog/exploring-state-of-the-art-llms-as-judges), via search summary; I did not open it).
  - None of these were trained or tested on coding-agent transcripts or on our rules.
- **Qwen3-8B**: 32,768 tokens natively, Apache 2.0, thinking mode on by default and switchable ([model card](https://huggingface.co/Qwen/Qwen3-8B)). General model, not judge-tuned. No published accuracy on this task.

## 3. Does the "short window, narrow yes/no" design work?

**Partly supported, not proven for our rules.**

Supportive evidence:
- Decomposing a judgement into binary questions is an established technique: InFoBench scores instructions as a share of yes/no checks, and its authors report higher annotator consensus than with direct scoring ([InFoBench](https://arxiv.org/html/2401.03601v1)). I could not find the actual GPT-4 vs human agreement number. UNVERIFIED.
- RocketEval (above): giving a tiny model a checklist of 5 to 10 yes/no questions lifted agreement for Gemma-2-2B from 39.2% (direct) to 57.9%, and rank correlation with Chatbot Arena from 0.888 to 0.965. Narrowing the question helps small models a lot. But the checklist was written by GPT-4o per query and agreement at the instance level was still only about 58% to 61%. That is for chat-quality grading, not our rules.
- Lost in the Middle and the judge-bias results favour short inputs with the evidence at the edges. A window of a few turns keeps the decision point close to both ends.

Against:
- No paper I found reports accuracy of narrow yes/no checks on coding-agent rules. The numbers above are from other tasks. So the accuracy for our rules is **UNVERIFIED** and has to be measured on a labelled sample.
- Side-effect and "did something it shouldn't" checks scored precision of 6.6% to 14.1% in AgentRewardBench, even for GPT-4o and Claude 3.7 Sonnet. Absence-type rules ("did not ask") are in this category. Expect a lot of false positives unless the heuristic has already narrowed to a real candidate.
- Windowing loses context: whether the user already approved a choice three turns earlier, or whether a rule applied at all, may sit outside the window. The window must include the user message that triggered it and a short "earlier approvals" summary built by code.

## 4. Cost and latency for 50 sessions x 200 windows (10,000 windows)

Assumptions (all **Estimates**): 1,500 input tokens per window (rule text plus the few turns plus the question), 50 output tokens (a yes/no/unclear plus a short reason). So 15M input and 0.5M output tokens per rule asked. If you ask 5 rules per window in one prompt, input is shared but output grows. Real windows may be larger because tool results (diffs, file contents) are large; truncate them.

### Hosted Claude (prices from the [pricing page](https://platform.claude.com/docs/en/about-claude/pricing); Batch API gives 50% off)

| Model | Input / output per MTok | Estimate for 15M in + 0.5M out | With Batch API |
|---|---|---|---|
| Claude Haiku 5.5 (prompts up to 100k) | $0.10 / $0.50 | about $1.75 | about $0.88 |
| Claude Haiku 4.5 | $1 / $5 | about $17.50 | about $8.75 |
| Claude Sonnet 5.5 | $2 / $10 | about $35 | about $17.50 |

Whole-transcript alternative (Estimate): 50 sessions x 100k tokens = 5M input tokens per rule per pass. At Sonnet 5.5 that is about $10 per rule, which is cheap. The cost is not the problem for a hosted judge. The problem is accuracy on 100k-token inputs (section 2) and that every call sends the user's private transcripts to a third party, so it must stay opt-in and say so.

Latency: UNVERIFIED. I did not run any API. Batch is asynchronous and I did not measure turnaround.

### Local LLM via Ollama

- No trustworthy published prefill figure for Qwen3-8B on Ollama for Apple Silicon. The sources I found give decode estimates only (for example about 112 tok/s decode on an M4 Max, a blog claim, no method) and recommend measuring locally ([markaicode](https://markaicode.com/benchmarks/ollama-qwen-3-m4-max-latency-benchmark/), [willitrunai](https://willitrunai.com/can-run/qwen-3-8b-on-m4-max-96gb)). Do not quote them.
- Cost in money: zero. Cost in time: UNVERIFIED. Time = 15M prompt tokens / your measured prefill rate. Measure with a 100-window pilot before deciding what to promise. Prompt caching of the shared rule prefix will help; whether Ollama reuses it across calls here is UNVERIFIED.
- Thinking mode multiplies output tokens. Turn it off for yes/no checks (documented switch: `enable_thinking=False` / `/no_think`).
- Requires the user to have Ollama and a model pulled (roughly several GB). Opt-in.

### Laya

- README figures: 32.8 to 39.5 ms per question on a T4; 453 ms for four questions on CPU, 146 ms on MPS, on a short email. Estimate: at 10,000 windows x 4 questions, roughly 75 minutes on CPU or 25 minutes on MPS if windows stay short. Longer inputs cost more (1.7 s for 4,000 tokens on Apple GPU). Cheap in time, but accuracy is the blocker (section 1).

### Heuristics only

- Pure code over JSONL. Seconds to a few minutes. No tokens. Deterministic and testable.

## 5. Recommended design

1. **Layer 1, always on, no model.** Count signals from the transcript:
   - decision points: user message with a choice, assistant plan with alternatives, first edit or commit after a plan;
   - `AskUserQuestion` calls (were options and a recommendation present: countable);
   - edits or commits with no ask between decision point and action;
   - for "fix everything found": findings listed in a review message vs follow-up edits;
   - for "no invented data": numbers in the final message with no matching tool result, and presence of "estimate" labels (regex-level only);
   - for "smallest change": diff size, files touched, vs the task. Report as numbers, not as a verdict.
   This is the base report. Say plainly what each count can and cannot mean.
2. **Layer 2, optional judge, windows only.** For each candidate window the heuristics found (a few turns around the decision point, tool results truncated, plus a code-built note of earlier user approvals):
   - one rule, one yes/no/unclear question, short rubric with 1 or 2 examples from the rule's own text;
   - no reasoning chain on local models; fixed temperature; run twice with a different order of options and keep only agreeing answers, treat disagreement as "unclear" (guards against position bias, which RocketEval identifies as a main small-judge weakness);
   - cap window size (stay well under 8k tokens so even an 8k-context judge like Flow-Judge is in range).
3. **Report honestly.** Judge output goes in a "needs a look" list with the quoted window, not in a score. Show the judge's agreement rate with the owner's own labels once measured.
4. **Calibrate before trusting.** The owner labels about 50 to 100 windows once (yes/no on each rule). Measure precision and recall per rule per judge. Only enable a rule's judge if it clears a bar the owner picks. This is the only way to get a real accuracy number for our case. No such number exists in the literature I found.
5. **Judge choice.**
   - Default: local Ollama, Qwen3-8B (non-thinking) or Selene-1-Mini. Both Apache 2.0. Neither has verified accuracy here; pick by the pilot.
   - Opt-in upgrade: hosted Claude, Haiku-class first (cheapest by far at window scale), batch mode. Show the estimated cost and what is sent before running. Never run without the owner's yes.
   - Laya: out of scope. Revisit only if the owner accumulates labelled data and wants a tiny classifier for a single question.
6. **Do not** judge whole sessions in one prompt, and do not let any judge produce an overall "adherence score".
