## Evidence
- Google eng-practices, "Small CLs": one self-contained change; "100 lines is usually a reasonable size for a CL, and
  1000 lines is usually too large"; file spread matters (200 lines in one file may be fine, across 50 files not).
  Splits: stacking, by files/reviewers, horizontal layers, vertical slices. Refactors in their own CL; tests in the
  same CL; deleting a file and trusted generated changes count as small.
  https://google.github.io/eng-practices/review/developer/small-cls.html
- Google case study (Sadowski et al., ICSE-SEIP 2018): median change ~24 lines, ~90% touch <10 files (figure from
  secondary sources; not checked in the paper text). https://research.google/pubs/modern-code-review-a-case-study-at-google/
- SmartBear/Cisco (2006, vendor-run, one company, 2500 reviews): review 200-400 LOC at a time; defect finding falls
  beyond ~400 LOC and above ~500 LOC/hour. https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/
- Merge-time evidence is mixed (Greptile, 25k PRs; arXiv 2203.05045). Vendor stacked-PR figures (Graphite) unverified.

## Owner decisions (2026-11-02)
- Own spec after M3 (research, owner input, spec, plan, build), like the memory feature.
- Strength: guide + ask at PR — a `pr-ship` skill plans the split; the guard asks when the agent runs `gh pr create`
  over the limit; unattended runs are refused.
- Limit: aim for <=200 changed lines, ask above 400 lines or 20 files; configurable per repo.
- Counting (corrected by the owner 2026-11-02): tests count. Everything counts except lockfiles and non-critical
  files such as `.gitignore` and other ignore files (e.g. `.prettierignore`, `.dockerignore`).
- Open for the spec: whether snapshots, `multi_file_gate.generated` paths and whole-file deletions count (Google treats
  deletions and trusted generated changes as small).
