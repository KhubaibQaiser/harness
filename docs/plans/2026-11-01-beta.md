# Harness beta implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** turn the M1 harness into a beta that test users install into any git repo through a Claude Code plugin or `npx`, with clean uninstall, CI on three operating systems, and an npm release pipeline.

**Architecture:**
- The deterministic CLI gains `init`, `uninstall`, `update`, `doctor` and `status`.
  - `init` is built from four units: `detect` (repo facts), `preset` (a config built from those facts), `merge` (one function per target file that renders the new content) and `apply` (a transactional write with backups, a manifest and rollback).
- The npm package root is also the Claude Code plugin root.
  - Its skills run the bundled `dist/cli.mjs`.
  - The private repo's `marketplace.json` points at the npm package.
- The hook runtime from M1 is hardened, but its shape doesn't change.

**Tech stack:** TypeScript and Node ≥ 22.11, esbuild bundle, Vitest; `yaml` and `picomatch` are bundled as dev dependencies; `magicast` is new (Vitest config edits), also bundled; GitHub Actions.

**Spec:** `docs/specs/2026-11-01-harness-beta-design.md`, which amends `docs/specs/2026-10-30-harness-design.md`. Read both.

## Global constraints

- No runtime dependencies. Everything the CLI and hooks need is bundled by `build.mjs`, and `package.json` has no `dependencies` key.
- `engines.node`: `>=22.11.0`. CI covers Node 22 and Node 24 on `ubuntu-latest`, `macos-latest` and `windows-latest`.
- Cross-platform paths:
  - Repo-relative paths are stored and compared with `/` separators.
  - File-system calls use `node:path`.
  - No shell is used to run anything: always `spawnSync(cmd, argv)` without `shell: true`, except Windows `.cmd` shims, which are resolved explicitly (Task 4).
- Never read `.env*` files.
- Model output is never trusted. Any JSON from a skill goes through `validateConfig` (Task 3), with one retry, then stop.
- Copy rules for every message a user sees:
  - one short sentence on what happened
  - then the next step
  - no "please"
  - file paths in backticks
- Commit as `git -c user.name=khubaibqaiser -c user.email=khubaib.dev@gmail.com commit`, with explicit `git add` paths, no `Co-Authored-By` trailer and no generated-by footer. Branch: `feature/beta`.
- Installs are blocked by the global agent guard. Any new dependency is installed by the owner. Only `magicast` is planned (Task 9).
- Every existing M1 test keeps passing (430 at the start of this plan).

## Review focus

1. **`init` run from a subdirectory.** Expected: it resolves the repo root, writes there, and says so. Test: Task 10, `init from a subdirectory writes at the repo root`.
2. **A repo path with spaces or non-ASCII characters** (Windows `C:\Users\Jane Doe\my repo`). Expected: the hook command in settings still runs. Test: Task 8, `settings hook command quotes a project dir with spaces`, plus the Task 14 end-to-end test on a temp dir named `repo with spaces ü`.
3. **Ctrl-C or "no" at the confirm prompt, or a write failure halfway through.** Expected: no file changes and no leftover `.tmp` files. Tests: Task 7, `failure on the third write restores the first two and removes temp files`, and Task 10, `declining the plan writes nothing`.
4. **A monorepo whose root has no test script but whose packages do.** Expected: the Stop step suggestions come from the root scripts (the repo's own orchestration). If there are none, `init` suggests running each package's test through the package manager's recursive form: `pnpm -r test`, `npm test --workspaces`, `yarn workspaces foreach -A run test` for Yarn 2+ (`yarn workspaces run test` for Yarn 1), or `bun --filter '*' test`. Test: Task 6, `monorepo without root test script suggests recursive test`.
5. **Running `init` a second time.** Expected: a refusal that points to `update`, with no writes. Test: Task 10, `second init refuses and names update`.

**Interfaces:**
- Produces:

```ts
export interface PackageFacts { dir: string; name?: string; scripts: Record<string, string>; test: 'vitest' | 'jest' | 'none'; testConfig?: string }
export interface Facts {
  root: string;
  packageManager: 'npm' | 'pnpm' | 'yarn' | 'bun' | 'none';
  yarnBerry: boolean;
  packages: PackageFacts[];          // the root package first, then workspace packages, sorted by dir
  python: { present: boolean; tools: ('pytest' | 'ruff' | 'mypy' | 'black')[] };
  existing: { claudeMd: boolean; agentsMd: boolean; settings: boolean; settingsLocal: boolean; otherHooks: string[] };
  defaultBranch: string;             // from origin/HEAD, falling back to main, then master, then the current branch
  warnings: string[];
}
export function detect(root: string): Facts
```

- Detection rules:
  - Package manager:
    1. the `packageManager` field
    2. otherwise the lockfile: `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` or `bun.lockb`, or `package-lock.json`

  - Test framework: a `vitest` or `jest` dependency (any dependency field), or a config file (`vitest.config.*`, `vite.config.*` with a `test` key, `jest.config.*`, or a `jest` key in `package.json`).
  - Python tools: declared in `pyproject.toml`, in `[tool.<name>]` sections or dependency lists, or in `requirements*.txt`. Plain line matching, no TOML parser.

### Task 7: Transactional apply and manifest

**Files:**
- Create: `src/install/apply.ts`, `src/install/manifest.ts`, `src/install/text.ts`
- Test: `test/install/apply.test.ts`, `test/install/text.test.ts`

**Interfaces:**
- Produces:

```ts
export type Change =
  | { kind: 'create'; rel: string; content: string; mode?: number }
  | { kind: 'update'; rel: string; before: string; after: string; blocks: string[] };   // blocks: the exact text inserted, used by uninstall
export interface Manifest { version: string; createdAt: string; files: { rel: string; kind: 'create' | 'update'; hash: string; backup?: string; blocks?: string[] }[] }
export function applyChanges(root: string, changes: Change[], version: string, now?: () => Date, fs?: FsLike): Manifest   // throws ApplyError after a full rollback
export function readManifest(root: string): Manifest | null
// text.ts
export function eolOf(s: string): '\n' | '\r\n'
export function withEol(s: string, eol: '\n' | '\r\n'): string
export function jsonIndentOf(s: string): string | number
export const sha256: (s: string) => string
```

- Behaviour:
  - The backup goes to `.harness/backup/<ISO timestamp with : replaced by ->/`.
  - Each write goes to `<target>.harness-tmp`, then is renamed into place.
  - On any error:
    - restore every file already replaced, from its backup
    - delete every file already created
    - delete the temp files
    - delete the backup directory only if nothing is left to restore
    - throw `ApplyError` with the original cause
  - Symlinked target files, or symlinked parent directories inside the repo, are refused before any write. This is the M1 `checkLinks` behaviour.
  - The manifest is written last, through the same temp-and-rename step, to `.harness/manifest.json`.

  - `failure on the third write restores the first two and removes temp files`, using an injected `FsLike` that throws on the third `renameSync`
  - `refuses a symlinked target before writing anything`
  - `eolOf and withEol keep CRLF`
  - `jsonIndentOf detects tabs and 4 spaces`
- [ ] **Step 2: Run them and confirm they fail.**
- [ ] **Step 3: Implement.**
