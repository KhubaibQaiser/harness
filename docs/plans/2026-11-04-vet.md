# harness vet implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `harness vet <target>` pins a GitHub plugin or skill to a commit sha, fetches its tarball through `gh`, extracts it in-process under strict limits, and runs a deterministic scan. `/harness:vet` adds a fresh-context staff-reviewer judgement and a two-step yes before it prints the install command and a sha-pinned marketplace entry.

**Architecture:**
- `src/vet/target.ts` parses the target and resolves it to `repo@sha[:path]`. `src/vet/tar.ts` is a small ustar/pax reader on `node:zlib`. `src/vet/fetch.ts` downloads, applies the limits and writes `.harness/vet/tmp/<id>-<sha>/`. `src/vet/scan.ts` holds the rules and the context estimate. `src/vet/report.ts` holds the summary, the report file and the install text. `src/cli/vet.ts` wires them.
- Every `gh` and `claude` call goes through `Exec` (text) or the new `ExecBytes` (the tarball). Tests fake both and never touch the network.
- The AI step stays in the skill and reaches the CLI only through files, the same contract as recommend: `scan.json` (the `--json` output) and `vet-review.json`, checked by `harness validate vet-review`.
- **`harness vet` is not an AI command.** It runs in any terminal and inside Claude Code. `refuseOutsideClaude` and `AI_FLAGS` in `src/cli/claude-only.ts` don't change. Only `/harness:vet` does the review.
- **The guard already allows `harness vet`**, because `vet` is not in `PERSON_ONLY` (`src/checks/guard.ts:58`). Task 8 pins this with tests and leaves the guard code as it is (spec §7).

**Tech stack:** TypeScript, Node ≥ 22.11, esbuild bundle, Vitest, `yaml` (already present), `node:zlib`. **No new dependency.** A tar reader is about 80 lines: 512-byte headers, octal sizes, checksums, and pax `x` records for long names. GitHub tarballs are `git archive` output (pax). Task 2 tests the reader against a real `git archive` tarball, so it is not only checked against the test's own writer.

**Spec:** `docs/specs/2026-11-04-vet-design.md` (owner-approved, binding). Section numbers below (§n) refer to it.

**Evidence for §10 field names:** https://code.claude.com/docs/en/plugins/marketplace-reference.md, "Plugin sources", fetched 2026-11-04. The page's table gives `github` the fields `repo`, `ref` and `sha` ("GitHub repository in `owner/repo` form"), and `git-subdir` the fields `url`, `path`, `ref` and `sha`. It also says the git-subdir "`url` accepts a full git URL or GitHub `owner/repo` shorthand", and that `sha` is "a full 40-character lowercase commit SHA". The spec's two entries match exactly: `{ "source": "github", "repo", "sha" }` and `{ "source": "git-subdir", "url", "path", "sha" }`. No change is needed.

## Owner questions

The plan follows the recommended answer to each question. A different answer changes only the task named.

1. **The temporary folder outlives one CLI call (Task 8).** §3.5 deletes the folder "when the run ends". §5 has the reviewer read the flagged files "inside the temporary folder", after `harness vet --json` has exited.
   - **Recommended:** `--keep` leaves the folder and adds `dir` to the JSON (one field beyond §4's shape). `harness vet --finish` deletes it, and `harness vet --clean` deletes it when the skill stops early. Each new run of the same target also clears its own stale folder first. The "run" is then the skill run.
   - **Alternative:** each finding carries a ±3-line excerpt, and nothing is kept on disk. This drops the reviewer's file reads, but it changes §4's shape more and §5's steps.
2. **`name@market` catalog fallback (Task 1).** The catalog stores no marketplace names.
   - **Recommended:** when `market` isn't installed, match a catalog item whose `source.type` is `github` or `git-subdir` and whose `source.plugin === name`. Use its repo and path, and its catalog `sha` as the ref. The install text then gives only the pinned entry.
3. **Relative-path plugin sources (Task 1).** Most marketplace entries, the official one included, use `"source": "./plugins/x"`. §3.1 stops on any type that isn't `github` or `git-subdir`.
   - **Recommended:** treat `./x` as a git-subdir of the marketplace repo at the marketplace sha. That is one branch and one test.
   - **The plan as written follows the spec:** the relative-path source stops with a message naming the type. On a yes, Task 1 gains the step marked "Q3".

Plan decisions the spec leaves open (the owner can change them in review):
- Decompressed tarball cap: 100 MB (`LIMITS.unpacked`), against gzip bombs.
- Entry names that Windows can't write are skipped as `unsafe-archive` on every OS, so the result is the same on all platforms.
- The temporary folder holds its own `.gitignore` containing `*`, so a crash never leaves untracked files for `git add`. The installer's gitignore block doesn't change.

## Global constraints

- Input: GitHub repo or tree URL, `owner/repo[#ref]`, or `plugin@marketplace`. npm, PyPI, local paths and archives are out (D1).
- Pin: `gh api repos/o/r/commits/<ref> --jq .sha`. A 404 means not found; any other failure means could not verify. With no `gh`: `harness vet needs the GitHub CLI (gh).` (§3.2)
- Fetch: `gh api repos/o/r/tarball/<sha>` into `.harness/vet/tmp/<id>-<sha>/`. Limits: 25 MB compressed, 5,000 files. Symlinks, hard links, absolute paths and `..` are skipped and reported as **medium**. Files over 1 MB are listed but not read (§3.3).
- vet never runs, imports or requires anything from the item, and never uses its folder as a working directory (§7).
- vet writes only under `.harness/vet/` (§7). Reports stay in git (D8). Nothing is installed or tracked: no manifest, config or budget change (D6).
- Matched text: cut to 120 characters, control characters escaped with `esc()` (§4), and invisible or bidi characters escaped as `\uXXXX` (Review Focus 1).
- Terminal summary: at most 12 lines (§6). The report ends with the caveat line from §6, verbatim.
- High findings need a second, explicit yes in the skill (D3). The reviewer never lowers a severity (§5).
- Skill: under 40 lines, `disable-model-invocation: true`, runs only `node "${CLAUDE_PLUGIN_ROOT}/dist/cli.mjs"` and `mktemp -d` (lean context: only its name and description load).
- The staff-reviewer's frontmatter `description` doesn't change, so its always-loaded text doesn't grow.
- Tests:
  - TDD: red first.
  - Every `gh` and `claude` call is faked through `Exec` or `ExecBytes`. Never run `claude -p` or anything paid.
  - Windows-safe: use `path.join` for disk paths, keep repo-relative paths in posix form, and pin `init.defaultBranch` in any git fixture.
  - Hostile tarballs are built in the test, never committed as binaries.
- Process:
  - Each task is one small PR off `main`, on branch `feature/vet-<n>-<slug>`, merged in order.
  - Commit as `git -c user.name=khubaibqaiser -c user.email=khubaib.dev@gmail.com commit …`, with no AI trailer.
  - Each task checks README.md, and its PR body says "README: updated (…)" or "README: checked, no change".
- Gates: `pnpm typecheck` and `pnpm test` pass at the end of every task.

## Review focus

1. **Invisible characters reach the terminal raw.** `esc()` (`src/core/config.ts:88`) escapes control characters, but not U+200B to U+200F, U+202A to U+202E, U+2060 to U+2069 or U+FEFF. An `injection-text` finding would print the very characters it reports. The fix: `show()` escapes them as `\uXXXX` (Task 3 test).
2. **A crafted target or `scan.json` steers a path.**
   - `o/r#../../user`, a `?` in a ref, or a path with `..` would change the `gh api` endpoint. They are rejected before any call (Task 1 test).
   - A tampered `scan.json` given to `--finish` or `--install` could aim the report write outside `.harness/vet/`. Its `repo`, `sha` and `path` are validated again (Task 8 test).
3. **A gzip bomb.** A tarball under 25 MB can expand to gigabytes. `gunzipSync` gets `maxOutputLength: LIMITS.unpacked`, and vet stops with a message instead of filling the disk (Task 2 test).
4. **Many high findings and a 12-line cap.** With 9 high findings, the summary shows 5 and then `…and 4 more high findings in the report.` (Task 6 test).
5. **Entry names Windows can't write** (`aux.md`, `a:b`, a trailing dot, a backslash). They are skipped as `unsafe-archive` on every OS, the run goes on, and the result is the same on macOS and Windows (Task 2 test).

**Interfaces:**
- Consumes: `Resolved` and `vetId` (Task 1); `findOnPath` and `syncCommand` (already imported in `exec.ts`).
- Produces:
  - `export type ExecBytes = (cmd: string, args: string[], maxBytes: number) => { status: number; stdout: Buffer; stderr?: string; missing?: true; tooBig?: true }`.
  - `export const defaultExecBytes: ExecBytes`. It uses `spawnSync` with `encoding: 'buffer'`, `maxBuffer: maxBytes`, `timeout: 120_000` and `stdio: ['ignore','pipe','pipe']`. `error.code === 'ENOBUFS'` sets `tooBig`.
  - `export interface TarEntry { path: string; type: 'file' | 'dir' | 'symlink' | 'hardlink' | 'other'; data: Buffer }`.
  - `export function readTar(gz: Buffer, maxOut: number): TarEntry[]`.
    - It handles typeflags `0`/NUL, `5`, `2`, `1`, pax `x` (`path=`, `linkpath=`), pax `g` (skipped) and GNU `L` (long name).
    - It throws `Error('archive is corrupt')` on a bad checksum or truncation, and `Error('archive expands past <n> MB')` on `maxOutputLength`.
  - `export const LIMITS = { compressed: 25 * 1024 * 1024, files: 5000, fileBytes: 1024 * 1024, unpacked: 100 * 1024 * 1024 }`.
  - `export interface Fetched { dir: string; rel: string; files: string[]; skipped: { path: string; why: string }[]; large: string[] }`.
    - `dir` is absolute; `rel` is `.harness/vet/tmp/<id>-<sha>`.
    - `files` are the repo-relative posix paths actually written, sorted.
  - `export function fetchTarball(root: string, r: Resolved, exec: ExecBytes): Fetched | { error: string }`.
  - `export function cleanTmp(root: string, key?: string): void`. It removes `.harness/vet/tmp/<key>`, or the whole `tmp/` when no key is given, with `rmSync(…, { recursive: true, force: true })`.
