# Done contract: where the binding "task is done" verdict should live

Research date: 2026-11-13. This builds on `research-anthropic.md` and `research-industry.md` in this folder and does not repeat them. Where an earlier finding matters, it is cited as (RA §n) or (RI Fn.n).

The fact this report starts from (RA §1): a Claude Code Stop hook fails open on a crash or timeout, ignores `onFailure: block`, and has an 8-block cap.

Method: every quote was read today from the cited URL, with curl plus grep or WebFetch. NIST SP 800-53 text comes from NIST's own OSCAL JSON catalog (github.com/usnistgov/oscal-content). The SSDF text was extracted from the NIST PDF. GitHub-hosted docs were read with `gh api`. All quotes are under 15 words. Anything not read from a source is labelled **inference**.

## Findings

### 1. Separation of duties and two-person integrity

| Source | Quote | What it implies |
|---|---|---|
| NIST SP 800-53r5 **AC-5** Separation of Duties (csrc.nist.gov/pubs/sp/800/53/r5/upd1/final; OSCAL `ac-5`) | "reduce the risk of malevolent activity without collusion" | Split duties so that one actor can't both do the work and certify it. The duties to split are organization-defined (`ac-05_odp`). |
| NIST **CM-5(4)** Dual Authorization | "cannot occur unless two qualified individuals approve and implement such changes" | The control text itself says this "may also be known as two-person control". |
| NIST **CA-2(1)** Independent Assessors | assessors do not "assess their own work" | Impartiality is defined as not grading your own output. That maps directly onto agent self-verification. |
| NIST **SA-11** Developer Testing | "Produce evidence of the execution of the assessment plan" | The developer must produce test evidence. Self-testing is allowed as long as it leaves evidence. |
| NIST **SA-11(3)** Independent Verification | "to verify the correct implementation of the developer security and privacy assessment plans" | An "independent agent" verifies the developer's plan and evidence. This is a separate enhancement layered on SA-11, not a baseline requirement. |
| NIST SP 800-218 SSDF **PW.7.1** (nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf) | code analysis "either in a fully automated way or in conjunction with a person" | The organization chooses human review, automated analysis, or both. SSDF does not require a separate party for PW.7 or PW.8. |
| SSDF **PW.7.2** examples | "Perform peer review of code" (Example 1); static analysis "with a human reviewing the issues" (Example 4) | Peer and human review appear as examples, not mandates. |
| SSDF **PW.8.1** Example 1 | testing "within a sandboxed environment" | Tests run in a controlled place. |
| SSDF **PO.4.1** Example 3 | "the Definition of Done in agile SDLC methodologies" | SSDF itself ties security checks to the DoD. |
| SSDF **PO.4.2** Examples 3 and 4 | "Automate decision-making processes utilizing the criteria, and periodically review these processes." / "prevent any alteration or deletion of the information" | An automated verdict is endorsed. The evidence it rests on must be tamper-proof. |
| SSDF **PW.6.2** Example 3 | "Perform all builds in a dedicated, highly controlled build environment." | The build/check environment is separate from the developer's own. |
| OWASP SAMM Secure Build (owaspsamm.org/model/implementation/secure-build/) | "removing any subjectivity from the build process by striving for full automation"; maturity 3: "ensure that building non-compliant artifacts fails" | The mature state is a pipeline that fails non-compliant output. SAMM's verification practices (owaspsamm.org/model/verification/security-testing/) mix automated and "manual expert security testing". No independence requirement was found. |
| OpenSSF Scorecard Code-Review check (github.com/ossf/scorecard/blob/main/docs/checks.md) | "if the merger is different from the committer (implicit review)" | The industry scoring tool treats "a different person merged it" as the minimum evidence of review. |
| Scorecard Branch-Protection | review "is not feasible for all projects" (for example, few active participants) | A solo maintainer is an explicitly recognised exception. |

## Comparison of options A to D

Scale: High, Medium or Low. "Inf." marks an inference. Every other cell cites the source above or a section of the earlier research files.

| Option | Tamper resistance | Fail-open risk | Cost | Attended vs unattended fit |
|---|---|---|---|---|
| **A. In-session only** (Stop hook, self-verification) | **Low.** The verdict runs where the agent can write: tests, hooks, evidence files. Agent-written evidence is outside SLSA's trust boundary ("not by a tenant"). Agents hid changes from graders with git (RA §5). Self-grading fails (NIST CA-2(1), "assess their own work"; RI F6.6). | **High.** The Stop hook fails open on crash or timeout, ignores `onFailure`, and has an 8-block cap (RA §1). `--bare` and some cloud modes drop hooks (RA §1). | **Lowest.** Inf.: no extra process or infrastructure. It also gives the fastest feedback (Tyen et al., RI F6.2: models fix errors well once they are located). | Attended: good as a fast feedback loop, with a human watching. Unattended: poor. Anthropic says to "have a person approve the result at the end" (RA §4). |
| **B. Separate verifier, same environment** (`harness verify`, exit code is the verdict) | **Medium.** It is a fresh process, but it reads files the agent could change. Harbor calls a separate verifier a better "security boundary" than shared mode. METR hardens this case with a different OS user ("cannot access files ... owned by `root`"). Inf.: without a separate identity or baseline hashes, the agent can still edit the tests the verifier runs. | **Medium.** Inf.: an exit code can be fail-closed (anything other than an explicit pass is a fail), unlike a Stop hook. But if the agent or a hook is what invokes it, a skipped run gives no verdict at all. Compare GitLab: "requires the existence of a successful pipeline". | **Low to medium.** Inf.: local CPU and wall time, with no CI minutes. | Attended: good. It is the binding local verdict a human can read. Unattended: only as strong as whatever forces it to run. Inf. |
| **C. External system** (required checks, rulesets, another machine or identity) | **High, if configured right.** SLSA L2/L3: control-plane-generated, signing secrets out of reach of build steps. But: write tokens "can set the state of any status check" (pin the expected source); "a pull request can edit the workflow file" (claude-code-action docs); rules the agent's identity can bypass don't bind it (routines doc). | **Platform-dependent.** GitHub: a skipped job "will report its status as "Success"" (fails open); path-filtered workflows stay "Pending" (fail closed). GitLab: no pipeline or a skipped pipeline blocks by default (fail closed). | **Medium.** CI minutes and latency. Google won't run every test at presubmit because "it’s too expensive". Inf.: one more round trip per iteration. | Unattended: the standard answer. Copilot, Devin, claude-code-action, Anthropic routines and the C-compiler run all sit behind branch protection or CI. Attended: workable but slower than B. |

## Where standards converge

1. **The actor doesn't certify its own work.** The same rule appears in NIST CA-2(1) ("assess their own work"), AC-5 and CM-5(4), SLSA ("not by a tenant"), Google ("does what the author claims it does"), GitLab and Scorecard (merger ≠ committer), and every agent platform (Copilot "cannot approve or merge", Code Review "never approves or blocks").
2. **The evidence behind the verdict must be out of the actor's reach.** SLSA L3 keeps signing secrets away from user build steps. SSDF PO.4.2 says to "prevent any alteration or deletion". METR, Harbor and Terminal-Bench keep tests and scoring data hidden until after the agent stops. PaperBench re-runs the submission "in a fresh VM".
3. **Automate the verdict and keep humans for judgment.** SSDF says "Automate decision-making processes". SAMM says "building non-compliant artifacts fails". GitHub and GitLab gate merges on checks. Yet every platform and Anthropic's own guidance end with a human approving the merge.
4. **Fail closed is a configuration choice, not a default.** GitHub's skipped jobs count as success. GitLab blocks by default. Stop hooks fail open. in-toto needs an explicit `DISALLOW *`. Every standard that works fails closed only because someone set it to.
5. **A verdict is valid only for the exact state it checked.** GitHub requires checks on "the latest commit SHA". SLSA records the run. The claude-code-action docs say results "don't cover edits Claude makes".

**Where they disagree**
- **Must the verifier be a different party?** NIST SA-11 allows developer self-testing with evidence. SA-11(3) independence is an optional enhancement. SSDF PW.7.1 lets the organization choose fully automated analysis. Google lets an owner author with one LGTM. Scorecard exempts small projects. CM-5(4) and in-toto thresholds go further and require two parties.
- **How exhaustive must the gate be?** SWE-bench and RI F1.4 point to the full suite. Google runs a subset at presubmit for cost and catches the rest post-submit.
- **LLM critics.** Jules puts a critic in the loop before completion. Anthropic's Code Review is advisory only. The March 2026 Anthropic harness post (RA §3) dropped its evaluator for tasks within the model's own ability. Nobody makes an LLM judge the sole binding gate.
- **Trust model.** in-toto assumes honest functionaries. Sigstore needs someone to monitor the logs. SLSA L1 accepts self-generated provenance. These are graded levels, not a single bar.

## Recommendation (INFERENCE, not a sourced claim)

There should be one binding verdict, and it should live as far from the agent as the stakes require. A is never binding.

1. **A: advisory only.** Keep the Stop hook as a fast "you're not done, here's the failing test" nudge. Don't treat its silence as a pass: it fails open and caps at 8 blocks.
2. **B: the binding local verdict.** `harness verify` should be fail-closed: exit 0 only on an explicit, complete pass, and every crash, timeout, missing tool or zero-tests-run counts as a fail. It should check that test files, check config and the verify config match the base commit (by hash) before trusting a green run. It should write a verdict record keyed to HEAD SHA, which goes stale on any later edit. For attended runs, that is the "done" the owner reads.
3. **C: the binding gate for anything that merges, and for every unattended run.** Run the same `harness verify` as a required check. Required check jobs must have no job-level `if:` that can skip them, so a skip can't count as Success. Pin the check to an expected-source app. Make sure the workflow and verify config can't be changed by the PR under test (CODEOWNERS or a base-branch workflow). The agent should run under an identity that can't bypass the ruleset or post statuses.
4. **D: the owner approves the merge.** This is the one step that can't be automated. The agent's identity can't approve (Copilot model). The approver gets the verify record and log citations, not the agent's summary (Codex model). For a solo owner this is the one approval left (Scorecard's small-project case).

Net: **attended runs: B decides, the human confirms. Unattended runs: C decides, the human merges. A never decides.**

## Unverified

- **OWASP ASVS:** no requirement for verification by a separate party was found. ASVS was not read in depth. SSDF only cross-references ASVS ids (e.g. 1.14.3, 14.1), and those ids were not checked.
- **SAMM:** no independence requirement found on the three Verification practice pages read. The SAMM detailed activity pages were not read.
- **Whether GitHub `pull_request` workflows use the PR's own workflow file:** this rests on claude-code-action's "a pull request can edit the workflow file". It was not confirmed in GitHub's own docs in this pass. GitHub org-level "required workflows" in rulesets were searched for and not found on the rules page.
- **Terminal-Bench 2.0's official harness behaviour:** taken from the Harbor repo docs and the TB1 style guide. The tbench.ai task-overview page returned 404 to WebFetch.
- **Codex:** the evidence is from the May 2025 system card. The current Codex cloud UI and the launch post (403) were not verified.
- **Jules:** the docs fetched say nothing about CI checks or who merges. The plan auto-approval detail is still third-party only (RI Unverified).
- **Devin:** only the two docs pages above were read. Whether Devin waits for required checks before reporting done was not confirmed.
- **Copilot's extra approval for agent-identity PRs:** read from GitHub docs today. The date of the change was not checked.
- **Cost:** no source gives cost figures for options A to D. Every cost cell except Google's "too expensive" is inference.
- **SSDF has no separation-of-duties requirement in PW.7/PW.8:** this is a reading of absence in the extracted PDF text, not a statement by NIST.
- **NIST AC-5 and SA-11(3) parameters** (which duties, what independence criteria) are organization-defined. Nothing here says what a given organization sets.
